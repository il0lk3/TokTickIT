# Lab 3 AI Use & Reflection

A living document recording the key prompts used during Sprint 3. This document demonstrates how AI was utilized not just for code generation, but as a sparring partner for architectural decisions, deep debugging, and strict specification enforcement.

## 1. AI Assistant Details

- **Primary Tool:** Google Antigravity IDE (Gemini)
- **Role:** Design consultant, backend architect, and deep-stack debugger. 
- **Workflow:** Iterative pairing. Instead of blind code generation, the AI was fed error logs, database schema states, and terminal outputs to trace bugs across the full stack (Prisma → Express → React).

## 3. Workflow Observation

Rather than treating the AI purely as a code generator, I utilized it in a dual capacity: as a **Specification Agent** and a **Coding Agent**.

When acting as a **Specification Agent** (e.g., Issue 1), the AI was highly efficient at drafting massive amounts of structured text, but it struggled significantly with internal consistency. For example, it would specify that Admins could view the queue in `ui-spec.md`, but deny them access in the Authorization Matrix of `specification.md`. I had to manually intervene, cross-check its outputs, and force it to reconcile the documents. This proved that AI cannot be trusted to independently define a cohesive system architecture without strict human review.

When shifting to a **Coding Agent** (e.g., Issues 3-10), the AI was most effective when given raw terminal outputs (like Playwright failure logs) or when challenged on its design choices ("Why can Admins edit IT Priority?"). When tests failed, feeding the AI the exact trace allowed it to navigate from a frontend React test failure, through the API, directly to a Prisma schema constraint. 

This Spec-Driven Development (Spec-DD) approach ensured that the AI didn't just write generic CRUD code, but wrote code that rigidly conformed to the engineering contracts we established.
